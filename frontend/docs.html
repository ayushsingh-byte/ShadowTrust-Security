Introduction

ShadowTrust is a self-hosted security operations platform. It combines honeypot deception, live telemetry, rule-based detection, malware analysis and lab machines in one Docker Compose stack of twelve core containers.

Everything the console shows comes from the backend database. When a part of the stack is not configured, the console says so instead of filling the gap with placeholder numbers.

Quick start with Docker

The fastest way to run ShadowTrust. You only need Docker Desktop, or Docker Engine with the Compose plugin.

bash
# 1. Clone the repository
git clone https://github.com/ayushsingh-byte/ShadowTrust-Security.git
cd ShadowTrust-Security

# 2. Run the setup wizard
./setup.sh

# The wizard checks Docker, detects your platform, creates .env files,
# prepares data directories, builds the images and starts the stack.

# Then open:
# Console     http://localhost:5500
# API docs    http://localhost:8000/docs
# MobSF       http://localhost:5055
# phpMyAdmin  http://localhost:8081
# Status      http://localhost:8000/health   (only with HEALTH_PAGE=1)

Environment variables

Configuration lives in the repository root .env, created from .env.example by the wizard. The fields you are most likely to touch:

env
# Database (required)
MARIADB_ROOT_PASSWORD=change-me
MARIADB_DATABASE=shadowtrust
MARIADB_USER=shadowtrust
MARIADB_PASSWORD=change-me

# Lab provider: local Docker (default) or aws
INFRA_PROVIDER=local

# Splunk blue team page (optional)
SPLUNK_API_URL=https://host.docker.internal:8089
SPLUNK_USER=admin
SPLUNK_PASSWORD=

# Malware engines (optional)
VIRUSTOTAL_API_KEY=
CAPE_URL=

# Local development only. Keep both at 0 on anything shared.
HEALTH_PAGE=0
DEV_BYPASS=0

Keep DEV_BYPASS at 0 outside your own machine. It exists to make local development faster, not to be left on.

Roles and access levels

ShadowTrust uses six roles with clearance levels. Admin routes are checked by the API, so hiding a button is never the only protection. Promote the first Super Admin directly in MariaDB, or through phpMyAdmin on port 8081:

sql
-- Promote the first user to SUPER_ADMIN
UPDATE users SET role = 'SUPER_ADMIN', clearance_level = 3
WHERE email = 'your@email.com';
super_adminClearance 3. Every page and route, including users and system settings.
overseerClearance 3. Admin panel, user and credential management.
auditorClearance 2. Admin panel, audit log, incidents and evidence.
analystClearance 2. Works incidents and evidence.
specialistClearance 2. Default role for clearance 2 sign-ups.
operativeClearance 1. Default role for clearance 1 sign-ups.

Authentication

Every API call needs a JWT bearer token. The login endpoint takes form fields, OAuth2 style, not JSON.

python
import requests

API = "http://localhost:8000/api/v1"

resp = requests.post(f"{API}/auth/login", data={
    "username": "operator@example.com",
    "password": "your-password",
})
token = resp.json()["access_token"]
headers = {"Authorization": f"Bearer {token}"}

Ingesting events

Sensors normally reach the database through the log collector. External agents can push events directly instead. The endpoint takes a list and requires an admin role.

python
events = [{
    "attacker_ip": "203.0.113.24",
    "event_type": "cowrie.command.input",
    "honeypot_type": "cowrie",
    "protocol": "ssh",
    "target_port": 2222,
    "session_id": "sess_abc123",
    "commands": "cat /etc/passwd",
    "risk_score": 8.5,
}]

requests.post(f"{API}/events/ingest", json=events, headers=headers)

Lab machines

Labs run through whichever provider INFRA_PROVIDER selects: local Docker by default, EC2 when set to aws. The request looks the same either way.

python
lab = requests.post(f"{API}/vm/launch", json={
    "environment": "kali",     # or "windows"
    "profile": "standard",     # light, standard, heavy
    "protocol": "rdp",         # rdp or ssh
}, headers=headers).json()

print(lab["lab_id"], lab["status"])

# Terminate when finished
requests.post(f"{API}/vm/{lab['lab_id']}/terminate", json={}, headers=headers)

Make targets

Shortcuts from the repository Makefile. Run make help for the full list.

bash
make setup          # first-time setup, same as ./setup.sh
make up             # start containers without rebuilding
make down           # stop containers, keep data volumes
make rebuild        # rebuild images and restart
make logs           # tail every container
make logs-backend   # backend logs only
make status         # container status
make shell-backend  # shell inside the FastAPI container
make db-shell       # MariaDB prompt inside the db container
make labs-up        # build the Kali image if needed, start everything
make test           # backend test suite (needs the db container)
make clean          # stop containers, remove local images
make nuke           # DESTRUCTIVE: also removes volumes and databases
